# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DoYouUnderstand is a native iOS SwiftUI app (Swift 5.0, iOS 26.0 deployment target) that analyzes a pasted/photographed message and either explains its subtext/tone or drafts a reply in one of 15 tones. New users first go through an 11-step onboarding funnel (name, age, gender, app theme pick, a "which message triggers you" quiz, a fake analysis/loading screen, a stats screen, a press-and-hold gesture step, a privacy screen, and a paywall) before landing on the Dashboard. Analysis is powered live by Gemini through a Supabase Edge Function (`supabase/functions/analyze-message`) so the Gemini API key never ships inside the app; history is persisted on-device as JSON. Subscriptions are real, wired through RevenueCat (a free trial + Monthly/Annual plans), and the whole app re-skins live through a theme system (3 app themes × 5 tone-color palettes) that starts out matching the device's own Light/Dark setting. There is a single Xcode project with one app target and two test targets.

## Communication Protocol (User Alerts)

I am not always looking at the screen. You must notify me of your status via the terminal using the `ntfy.sh` curl command. All cases below use the same command shape — only the emoji prefix and the message content change. The message must always be a real 1-sentence summary written for that specific moment (what was actually done, or what you actually need), never the generic placeholder text shown in the examples.

1. When a task is 100% complete:
Run this command, replacing the message with a 1-sentence summary of what you actually finished:
`curl -d "✅ Claude: <1-sentence summary of what was done>" ntfy.sh/dyu_claude_alerts_4848`
Example: `curl -d "✅ Claude: Rewrote the paywall CTA as a glassmorphism button and verified it in light/dark UI tests." ntfy.sh/dyu_claude_alerts_4848`

2. ALWAYS, before any action that will trigger a permission prompt:
This is not optional and has no exceptions. Any tool call that the harness will pause on for my approval (a Bash command, an Edit/Write, anything outside what's pre-approved) must be preceded by this notification, run in the turn *before* you attempt that action — never attempt the action first and notify only if it blocks. I am not watching the screen, so an unannounced prompt just sits there locked with no way for me to know it's waiting. Replace the message with a 1-sentence summary of exactly what you're about to do and are asking permission for:
`curl -d "⚠️ Claude: <1-sentence summary of the action awaiting your approval>" ntfy.sh/dyu_claude_alerts_4848`
Example: `curl -d "⚠️ Claude: About to run a destructive git command — approve when ready." ntfy.sh/dyu_claude_alerts_4848`

3. When you need my input or are stuck:
If you encounter an error you cannot fix or need me to make a decision (not a permission prompt - an actual judgment call), run this command FIRST — replacing the message with a 1-sentence summary of exactly what you need — before waiting for my reply in the chat:
`curl -d "⚠️ Claude: <1-sentence summary of what you need>" ntfy.sh/dyu_claude_alerts_4848`
Example: `curl -d "⚠️ Claude: Need your OK before splitting the paywall into two onboarding steps." ntfy.sh/dyu_claude_alerts_4848`

4. Screenshots are opt-in, not automatic:
Do NOT take or send screenshots by default after visual changes - getting one usually means running the UI test suite (or a one-off UI test) to drive the Simulator into the right state, and that's slow and violates the "never run UI tests automatically" rule below. Only capture and send a screenshot when I explicitly ask for one in that turn (e.g. "show me a screenshot", "send a screenshot of X"). Otherwise just describe the change in text and let me ask if I want to see it.

## Commands

Build (Debug, simulator):
```bash
xcodebuild -project DoYouUnderstand.xcodeproj -scheme DoYouUnderstand \
  -destination 'platform=iOS Simulator,name=iPhone 17' build
```

CRITICAL TESTING PROTOCOL:
UI Tests (`DoYouUnderstandUITests`) take ~3+ minutes each and severely slow down the feedback loop.
- NEVER run UI tests automatically while working on tasks.
- ONLY run Unit tests to verify standard code logic.
- Run UI tests ONLY if the user explicitly states: "Run the UI tests."

Run ONLY Unit Tests (Fast - Use this by default):
```bash
xcodebuild -project DoYouUnderstand.xcodeproj -scheme DoYouUnderstand \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:DoYouUnderstandTests test
```

Run a single test (Swift Testing framework, not XCTest):
```bash
xcodebuild -project DoYouUnderstand.xcodeproj -scheme DoYouUnderstand \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:DoYouUnderstandTests/DoYouUnderstandTests/example test
```

Run UI Tests (SLOW - Only run if explicitly asked by user):
```bash
xcodebuild -project DoYouUnderstand.xcodeproj -scheme DoYouUnderstand \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:DoYouUnderstandUITests test
```

There is no CLI linter/formatter configured in the repo (no SwiftLint config present). List available simulator destinations with:
```bash
xcodebuild -showdestinations -project DoYouUnderstand.xcodeproj -scheme DoYouUnderstand
```

Unit tests (`DoYouUnderstandTests`) use `import Testing` / `@Test` / `#expect(...)` (Swift Testing), not XCTest. UI tests (`DoYouUnderstandUITests`) use standard `XCTest`/`XCUIApplication`.

## Architecture

Most features follow the same four-file MVVM-ish pattern under `Features/<FeatureName>/` (Onboarding is the one exception — see below):

- **`<Feature>StateModel.swift`** — an `@Observable final class StateModel` nested as an extension of the ViewModel (`extension DashboardViewModel { @Observable final class StateModel: StateModelProtocol { ... } }`), holding the plain data the view renders.
- **`<Feature>ViewModel.swift`** — `@Observable final class` conforming to `StateViewModelProtocol` (`Shared/State/StateViewModel.swift`). Owns `stateModel`, `state: ViewState<StateModel>`, an `Actions` struct of closures the view calls into, and an `Output` enum for events that bubble up to navigation. Business logic that mutates `stateModel` lives in a `// MARK: - Functions -` extension; wiring closures lives in a `// MARK: - Actions -` extension via `setActions()`.
- **`<Feature>Screen.swift`** (under `Views/` for Dashboard) — a `View` that owns `@State var viewModel`, renders `StateScreen(state: viewModel.state) { stateModel in ... }`, and a nested `ContentView` that takes `stateModel` + `actions` as plain values (keeps previews/content stateless and easy to preview in isolation).
- **Mocks** — only `FAQ` (`Models/FAQItem+Mocks.swift`) and `Input` (`PickedImage+Mocks.swift`) still have per-feature static mock data gated behind a `useMocks: Bool` flag on the ViewModel. `Dashboard`/`Explanation`/`Reply` no longer take a `useMocks` flag at all — they're driven live by `HistoryServiceProtocol` (see History below) and the real Gemini-backed service. `Settings`'s top-level screen and `Onboarding` still accept `useMocks: Bool` in their initializer for interface consistency, but neither currently branches on it. `Input`'s `useMocks` only gates a Simulator-only fallback for capturing a photo when no camera hardware is present — the actual analysis call is always live.

Shared infrastructure lives in `Shared/`:

- **`Shared/State/`** — the `ViewState<StateModel>` enum (`.loading` / `.loaded` / `.error`), `StateModelProtocol`, `StateViewModelProtocol`, and `StateScreen<StateModel, Content>` (the generic loading/error/content switcher every screen wraps its content in).
- **`Shared/Navigation/NavigationManager.swift`** — a single `@Observable` router owning a `NavigationPath`. Screens never navigate directly; they call `output(...)` closures. `ContentView.swift` is the single `NavigationStack` root: each `Screen` is constructed with an `output` closure that forwards into `router.handle(.featureName(output))`, and `NavigationManager` translates each feature's `Output` enum into `navigate(to: Route)` / `popBack()` calls. `Route` is the app-wide `Hashable` enum of destinations. To add a new screen: add a `Route` case, add a `FlowEvent` case + `handle*` function in `NavigationManager`, and add the `navigationDestination` case in `ContentView`.
- **`Shared/Theme/AppTheme.swift`** — the only source of colors/fonts (`Theme.Colors.Main/Text/Tone`, `Theme.Typography`). Colors are no longer static asset-catalog lookups — every `Theme.Colors.*` property is a computed `var` reading `ThemeManager.shared`, so the whole app re-skins live (including mid-onboarding, with zero call-site changes needed) the instant the current theme/palette changes. `Theme.Colors.Tone` has 15 computed colors, one per `Tone` case (its internal helper module-qualifies the parameter as `DoYouUnderstand.Tone` since the bare name would otherwise resolve to the enclosing `Theme.Colors.Tone` namespace itself). Typography is built from two custom variable fonts (not system fonts): `Theme.Typography.spaceGrotesk(size:weight:)` for titles/headlines/big numbers/buttons, and `Theme.Typography.inter(size:weight:)` for body copy/labels — the named tokens (`heroTitle`, `bodyText`, etc.) are just pre-built calls to those two helpers. Always reference `Theme.*` rather than hardcoding `Color(...)`/`Font.custom(...)` in views.
- **`Shared/Theme/ThemeManager.swift`** — the single source of truth for the app's current visual theme: an `@Observable` singleton holding `appTheme: AppThemeChoice` and `tonePalette: TonePaletteChoice`, both persisted to `UserDefaults` on `didSet`. Before the user has ever picked anything, `appTheme` defaults to the device's actual Light/Dark appearance (`AppThemeChoice.systemPreferred`, via `UITraitCollection.current.userInterfaceStyle`) rather than hardcoding Dark, and `tonePalette` defaults to `.classic`.
- **`Shared/Fonts/`** — the two bundled variable font files (`Inter-VariableFont_opsz,wght.ttf`, `SpaceGrotesk-VariableFont_wght.ttf`) plus their OFL licenses, and `AppFonts.swift`, whose `AppFonts.registerAll()` is called once from `DoYouUnderstandApp.init()` to register them with CoreText (`CTFontManagerRegisterFontsForURL`) at launch.
- **`Shared/StaticData/AppLayout.swift`** — shared spacing/sizing constants (`StaticData.Layout.*` and `CGFloat.space0...space32`). Use these instead of magic numbers in view padding/frames. (`AppStrings.swift` only has a handful of Dashboard strings — most feature copy is written inline in the view files.)
- **`Shared/Services/GeminiService.swift`** — live, not a stub: an `enum` of `static func`s (`explain`, `reply`, `replyForTone`, `tweak`) that POST JSON to the `analyze-message` Supabase Edge Function and decode the response into feature `Payload` types, converting tone strings to `Tone(rawValue:)` (throws `ServiceError.invalidResponse` if the server ever returns a tone string that doesn't match a case in `Shared/Models/Tone.swift`, so the two must stay in sync). `reply`/`replyForTone` also take a `targetLanguage: ReplyLanguage` param (default `.autoDetect`) forwarded to the server as-is. The shared private `invoke(_:)` automatically retries a failed request up to twice with a short delay before giving up — the first Gemini call of a session occasionally fails (most likely a cold Supabase Edge Function start or a transient upstream 429/503), and a silent retry usually succeeds without the user ever seeing the failure. **`Shared/Services/SupabaseManager.swift`** holds the project URL and anon key and builds Edge Function URLs. The actual prompt-building/Gemini-calling logic lives server-side in `supabase/functions/analyze-message/index.ts` (Deno) — deployed independently via `supabase functions deploy analyze-message`; editing that file in the repo does **not** update the live function until it's redeployed. The Gemini API key is only ever set as a Supabase secret, never committed.
- **`Shared/Services/ReplyLanguagePreferenceStore.swift`** — `@Observable` singleton persisting the user's global "Default Reply Language" (`ReplyLanguage`: `.autoDetect`/`.english`/`.polish`), set from Settings > Language. Read by `InputViewModel` (initial reply batch) and `ReplyViewModel` (new on-demand tones) as the `targetLanguage` sent to Gemini. This is about what language *Gemini writes replies in* - separate from `LanguageChoice`/`LocalizationManager` below, which control the *app's own UI language*. The Reply screen's per-card Tweak panel has its own `[ PL | EN ]` toggle (`ReplyOption.activeLanguage`) that overrides a single card's language for that session only and never writes back to this store.
- **`Shared/Localization/LocalizationManager.swift`** — `@Observable` singleton (same pattern as `ThemeManager`) holding `currentLanguage: LanguageChoice`, persisted, defaulting to `.english`. `ContentView` reads `LocalizationManager.shared.locale` and injects it as `.environment(\.locale, _)` on the root `NavigationStack`, which is what makes every `Text("literal")`/`Button("literal")`/`.alert("literal", ...)` in the app re-resolve against **`DoYouUnderstand/Localizable.xcstrings`** live the instant the user picks a different language in Settings > Language - no relaunch, independent of the device's own system language. Also exposes `Loc.t(_:)`, a small helper (`String(localized:locale:)` under the hood) for any string that *isn't* a compile-time `Text("literal")` - most commonly an enum's computed property consumed as `Text(someEnum.someProperty)` (`Text(String)` does **not** auto-localize; only the literal-driven `Text(LocalizedStringKey)` initializer does). The convention used throughout the codebase: wrap a `switch`-derived string at its declaration with `Loc.t("English text")` (see `Tone.replyTitle`/`.definition`, `AppThemeChoice.title`, `TonePaletteChoice.title`, `GenderChoice`/`TriggerMessage`/`PricingPlan` in `OnboardingStateModel.swift`, etc.), or wrap the *consuming* `Text(param)` inside a reusable component with `Text(LocalizedStringKey(param))` when the same component is fed many different literal titles by different call sites (see `SettingsRow`, `ActionLabel`/`SelectionCard`, `BreakdownTile`, `FAQRow`, `PolicySectionView`). A handful of enums (`Tone`, `GenderChoice`, `PricingPlan`, `AnalysisType`, `ReplyLanguage`) have a **separate** `displayName`/`title` computed property specifically because their `rawValue` must stay the fixed English string used for `Codable` persistence, `UserDefaults`, or the Gemini Edge Function contract - never route `rawValue` itself through `Loc.t()`. Interpolated strings that mix translatable words with a dynamic value (e.g. "STEP 3 OF 10") are rewritten as `String(format: Loc.t("STEP %d OF %d"), x, y)` rather than a plain `Text("STEP \(x) OF \(y)")`, so the catalog key is exact and unambiguous rather than relying on Swift's auto-generated interpolation key. Only `.english`, `.polish`, and `.spanish` have real translations today (per user-facing text, not full 6-language `LanguageChoice` coverage) - any other `LanguageChoice` falls back to English for untranslated keys, which is a String Catalog's normal, safe behavior for a missing localization, not a bug.
- **`Shared/Services/SubscriptionManager.swift`** — `@MainActor @Observable` wrapper around the RevenueCat `Purchases` SDK: fetches the current `Offering`, tracks whether the `pro_access` entitlement is active (`isProUnlocked`), and exposes trial/renewal info (`isInFreeTrial`, `currentPeriodEndsAt`, `willRenew`) read off the active `EntitlementInfo` in `CustomerInfo`. Drives both the onboarding paywall (`FinisherStepView`) and Settings > Manage Subscription.
- **`Shared/Services/UsageLimiter.swift`** — a silent daily cap (30/day, not shown anywhere in the UI) on Gemini-backed calls (explain/reply/tweak/generate-more-tones), tracked via `UserDefaults` and reset by calendar day. Exists purely to stop a single abusive/spamming user from burning through the Gemini budget — replaces an earlier, visible "N free scans" quota model. A blocked call shows a pleasant "come back tomorrow" alert instead of hitting the network; `Features/Settings/PrivacyPolicy` mentions a generic "fair use" limit exists without stating the number.
- **`Shared/Services/UserProfileStore.swift`** — persists the name/age/gender first collected in onboarding to `UserDefaults` (no backend yet), so Settings > Profile has something real to show and edit.
- **`Shared/Components/BouncingDotsLoader.swift`** — a 3-dot bounce loading indicator, used in place of the native `ProgressView` spinner in a few spots.
- **`Shared/Components/FlowLayout.swift`** — a custom `Layout` that wraps subviews left-to-right, top-to-bottom into as many rows as needed to fit the proposed width (a tag-cloud/flow layout). Used by Reply's tone quick-jump pill row, where the pill count (up to 16) isn't known at design time.
- **`Shared/History/`** — `HistoryServiceProtocol` (`fetchAll`/`fetch(id:)`/`save`/`delete`) has two implementations: `LocalHistoryService` (the default, real on-device JSON persistence under Application Support — no network) and `MockHistoryService` (in-memory seed data, used for SwiftUI Previews). `HistoryServiceProvider.shared` is the single switch between them — flip the one commented-out line in that file to swap the whole app onto mock data.
- **`Shared/Models/`** — cross-feature domain enums: `AnalysisType` (`.explain` / `.reply`), `Tone` (16 cases — see below), `AppThemeChoice` (`.light`/`.dark`/`.terminal` — all three are real, fully-defined neutral palettes now; picking Terminal also auto-switches `TonePaletteChoice` to a matching Terminal tone palette, though the user can still override that manually), `TonePaletteChoice` (`.classic`/`.pastel`/`.neon`/`.mono`/`.terminal` — a real, live re-skin of every `Theme.Colors.Tone.*` value app-wide, not a decorative preview; independent from `AppThemeChoice`, so e.g. a Light app theme can be paired with a Neon tone palette), and `LanguageChoice` (6 languages — drives the app's actual UI language via `LocalizationManager`; only English/Polish/Spanish have real translations in `Localizable.xcstrings` so far, the other 3 fall back to English).

`Tone` (`Shared/Models/Tone.swift`) has grown to **16 cases**: `anxious`, `condescending`, `overEager`, `passiveAggressive`, `sarcastic`, `professional`, `assertive`, `friendly`, `playful`, `apologetic`, `empathetic`, `blunt`, `flirty`, `diplomatic`, `dismissive`, `savage`. Every property (`color`, `emoji`, `replyTitle`, `tweakLowLabel`, `tweakHighLabel`, `definition`) is an exhaustive `switch` over `self`, so the compiler forces you to fill in all six for any new case. `Tone.initialReplyBatch` is a fixed 5-tone contrasting set (`professional`, `assertive`, `friendly`, `diplomatic`, `empathetic`) requested on the very first reply generation (`InputViewModel`), so the first result comes back fast instead of waiting on all 16. The Reply screen then shows a `FlowLayout` row of colored one-word pills ("GENERATE A SPECIFIC TONE") for every tone not yet generated; tapping one removes it from the pill row, inserts a pulsing `ReplyOptionSkeletonCard` at the top of the results list, and fires a single-tone Gemini call (`GeminiService.replyForTone`, Edge Function mode `replyForTone`) that swaps the skeleton for a real `ReplyOptionCard` on completion (or drops it and re-offers the pill on failure) — `ReplyStateModel.pendingTones` tracks in-flight taps, and both `options`/`pendingTones` are animated via `.animation(.spring(...), value:)`. Once every tone has been generated the pill row is replaced by a static "That's every tone we've got!" card. A floating scroll-to-top button (via `.onScrollGeometryChange`) appears once the user has scrolled far enough down. Each card's Tweak panel also has a `[ PL | EN ]` `LanguageTogglePill` - tapping it flips that one card's `activeLanguage` and regenerates just that card via `GeminiService.replyForTone(targetLanguage:)`, session-only (see `ReplyLanguagePreferenceStore` above). The Edge Function's own `TONES` list (`supabase/functions/analyze-message/index.ts`) must stay in sync with the Swift enum, but editing that file locally doesn't update the live function until it's redeployed (`supabase functions deploy analyze-message`).

### Settings (grown into a small sub-feature)

`Features/Settings/` now has its own `Route` cases and mini-features beyond the top-level `SettingsScreen` (a profile summary card + rows linking out to each of these): `Profile` (edit name/age/gender — staged locally, with a Cancel/Save bar that only appears once something's actually changed, backed by `UserProfileStore`), `ThemeSettings` (Settings' version of onboarding's theme step — reuses `OnboardingScreen.ThemePreviewCard`/`TonePaletteRow` directly, no `Continue` step, applies instantly), `LanguageSettings` (the app-UI language picker - see `LocalizationManager`/`LanguageChoice` above - plus a second, separate "Default Reply Language" section backed by `ReplyLanguagePreferenceStore` for what language Gemini writes replies in), `ManageSubscription` (plan status + trial/renewal countdown via `SubscriptionManager`, an in-app upgrade flow for free users reusing `OnboardingScreen.PricingPlanRow`, Restore Purchases, and a link out to Apple's native "Manage Subscriptions" page — cancelling or switching between Monthly/Annual is left entirely to that Apple UI, not reimplemented in-app), and `PrivacyPolicy` (static content). Each is a small instance of the usual four-file pattern.

### Onboarding (the exception to the four-file pattern)

`Features/Onboarding/` is a single 11-step, forward-only funnel (`OnboardingViewModel.StateModel.Step`: `greeting → name → age → theme → intro → triggerMessage → processing → stats → tactileHold → privacy → finisher`) with no back navigation. It outgrew the standard `StateModel`/`ViewModel`/`Screen` split into several files:

- `OnboardingStateModel.swift` / `OnboardingViewModel.swift` — the usual state/view-model pair, plus per-step option enums (`GenderChoice`, `TriggerMessage`, `PricingPlan`).
- `OnboardingScreen.swift` — the shell: progress header, footer (Continue/auto-advance), and the `switch` that routes to each step's view.
- `OnboardingScreen+IntroSteps.swift`, `+QuizSteps.swift`, `+ClosingSteps.swift`, `+Components.swift`, `+Animations.swift` — the actual step views and shared onboarding-only UI pieces (bar-chart counters, message bubbles, the press-and-hold "tactile" gesture, the `.onboardingReveal(delay:)` fade/slide-in modifier), grouped by where they sit in the funnel rather than one file per step.

`ContentView` decides once per app launch whether to start on onboarding (`isShowingOnboarding`, initialized from a `#if DEBUG` `debugAlwaysShowOnboarding` override if set, otherwise from the persisted `hasSeenOnboarding` `@AppStorage` flag) and only flips to the Dashboard when onboarding explicitly finishes — so completing the funnel always moves forward even on a debug build that always starts on onboarding. There's a `#if DEBUG`-only "Skip Onboarding" button on the greeting screen for fast iteration. The theme step defaults its selection to the device's actual Light/Dark appearance (see `ThemeManager` above) rather than nothing being pre-selected.

The paywall (`FinisherStepView`) has a real RevenueCat purchase flow: "START FREE TRIAL" calls `SubscriptionManager.purchase(_:)` for the selected `PricingPlan` (Monthly/Annual) and only completes onboarding once the purchase actually succeeds; "Restore Purchases" is wired too. That step now scrolls (the feature list + trial callout + an auto-advancing `PaywallFeatureTicker` + pricing rows + a savings line no longer reliably fit unscrolled on smaller screens), and a 3-hour discount window (`onboardingDiscountExpiresAt` in `UserDefaults`, started the first time the paywall is shown) drives a live countdown badge plus a per-plan "you'll save $X" line while active.

Features present: `Onboarding`, `Dashboard` (history list + entry point), `Input` (text/photo capture, choose explain vs. reply), `Explanation`, `Reply`, `FAQ`, `Settings` (see above). Dashboard's `HistoryItem.type: AnalysisType` determines whether tapping a history row routes to `.explenation(id)` or `.reply(id)` (note: `Route.explenation` is the existing, intentionally-matched spelling — don't silently "fix" it in isolation, it's used across `NavigationManager`/`ContentView`). Explanation's second interaction step ("THE BOTTOM LINE") is a pure toggle driven by `stateModel.interactionStep` — tapping "GOT IT!" flips back to the breakdown tiles rather than leaving the screen; only the header's back button does that.
